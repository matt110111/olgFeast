# Running a dinner event

For the configured four-kitchen, six-input demo, see [DEMO.md](DEMO.md).
The primary volunteer workflow is Menu → Check & collect → Kitchen.

Open **http://192.168.8.163:3000** in the tablet browser. Sign in with the
organizer account, or a volunteer/guest-tablet account created in **Event station → Setup**.
Existing passwords still work. Everyone needs to sign in again after this upgrade.

## Before guests arrive

1. In **Setup**, create an event with its name and date. Leave ticket collection
   confirmation enabled if volunteers collect physical tickets at the station.
   Turn it off if collection happens elsewhere; reports then show tickets owed
   with zero tickets recorded as collected.
2. Replace the sample menu with your real menu and tickets per portion. Mark
   sample items unavailable. Tickets are sold by your separate system; OlgFeast
   does not process payments or infer a dollar value for tickets.
3. Add ingredients and supplies using **g**, **ml**, or **each**. Convert bulk
   purchases to those units (2 kg = 2,000 g, 1 liter = 1,000 ml).
4. Set the recipe for one portion of each menu item. Include plates, cups,
   utensils, napkins, and other disposables as appropriate. Actual recipes are
   not assumed or generated by the app.
5. Record starting stock for the selected event, with a reason such as
   “Starting stock.” Record replenishment as positive quantities and additional
   waste as negative quantities. For a physical count correction, enter the
   difference between counted stock and the current estimated remaining stock.
6. Under **Tablet and volunteer accounts**, choose **Volunteer** for staff
   tablets or **Guest tablet** for guest-operated tablets. Use a separate account
   per tablet. Volunteers collect tickets and operate the kitchen; organizers
   manage setup and reports. Never leave a staff account signed in on a guest tablet.
7. On every tablet select the correct event, then choose **Take orders** or
   **Kitchen**. Place one small trial order and void it before preparation to
   check the whole path before the event opens.

## Kitchens and input stations

In **Menu & setup**, assign every menu item to exactly one kitchen. The configured
demo has Fried, Grilled, Cooked 1, and Cooked 2. All six input stations show the
full event menu. Volunteers check the combined ticket total, collect tickets on
the check screen, then send each kitchen its assigned items with one action.

Each check creates a separate order for each kitchen it uses. These orders share
a check number and input station number. All are saved in one transaction;
retrying a lost confirmation returns the same orders without collecting twice.
Each input station keeps its draft and receipt across reloads.

Kitchen tablets select their kitchen. Kitchen queues and stock reports remain
scoped to that kitchen. Whole-event reports combine them. Order counts count
kitchen orders; ticket totals count each ticket once. Room selection is an
operating filter, not an account permission boundary.

Guest accounts retain the separate ticket-desk workflow below. Sign into an
input volunteer account for collection on the checkout screen.

## Guest-operated tablets

Sign a guest tablet into its guest account and select the event. Guests choose
portions and tap **Send to ticket desk**. The screen shows their order number
and tickets owed; the number survives a reload until **Next guest** is tapped.
Guests should note the number before leaving the tablet. Use table numbers or
“Walk-up” on shared tablets; orders belong to the tablet account, so its order
history is shared rather than private to each guest. Guests using personal
accounts can also use this workflow.

At a volunteer tablet, open **Collect tickets**, match the order number, collect
the physical tickets, and tick the confirmation before sending it to the kitchen.
If a response is lost, refresh: confirmed orders leave this list. Retrying the
confirmation cannot double-count tickets. Never collect the same tickets twice.
Cancel abandoned orders from this tab, returning any tickets physically collected.

Orders awaiting tickets do not enter the kitchen or count toward consumable
usage, accepted portions, or accepted ticket totals. Reports list their count and
tickets separately. Menu prices and recipes are snapshotted when the guest submits;
confirmation uses those ticket values. If a food item becomes unavailable before
collection, cancel the order and have the guest choose again. Events cannot close
until waiting orders are confirmed and served or cancelled.

For this event workflow, leave **Require ticket collection confirmation** enabled.
If disabled for a future event, guest orders go directly to the kitchen and record
zero tickets collected. Legacy cart checkout redirects users to event ordering
while any event is open.

## During service on volunteer tablets

- Tap menu tiles to add portions. Use the large +/− buttons to correct quantities.
- Add an optional guest name or table number. Blank names become “Walk-up.”
- Tap **Check order**, read the ticket total, collect the physical tickets here, and check the confirmation.
- Tap **Send to kitchen** and wait for the green order number before serving the
  next guest. Tickets are never treated as preparation time.
- A lost response shows **Retry same order**. This uses the saved checkout
  reference and cannot create a second copy of the same order. Do not collect
  tickets again. Drafts and pending confirmations survive a page reload on
  that tablet; clear browser storage only after resolving pending orders.
- Kitchen volunteers advance orders through **Start preparing → Mark ready →
  Mark served**. The queue refreshes every five seconds and displays failures.
- Void an order only before preparation starts. Return any collected tickets.
  Voids remain in history and are excluded from ticket and consumption totals.
  Prepared food cannot be voided; its consumption remains recorded. Record
  additional waste as a stock adjustment, without subtracting the same food twice.

## Reports and closeout

The event report shows portions ordered and served, tickets owed and collected,
voids, and recipe-based estimated use. **Estimated remaining = net stock added −
recipe quantities on accepted orders**. This includes orders still in the
kitchen and excludes voided orders and guest orders awaiting tickets. It is an estimate, not a measured inventory
count or a food-safety record.

Missing recipes are explicitly listed. Adding a recipe later cannot reconstruct
those orders’ usage; recipe and ticket edits apply to new orders only. The prior
installation’s order is retained in **Order history** with no event assignment.
Its menu values were captured during migration; historic ingredient usage is
unknown.

Download the CSV after the event. It can be used alongside your separate ticket
sales report for reconciliation. The app records tickets collected on voided
orders so you can reconcile their return; it does not confirm physical refunds.
Close the event once all orders have been served or voided. Reopen it in Setup
if necessary.

## Tablets and local network

The app runs in the browser; no paid client app is required. Use iPads with Safari
or Android tablets with an up-to-date Chrome browser and working Wi-Fi. The frontend build targets
Chrome 90 or later. Browser tests cover WebKit at 1024×768 and 768×1024, plus
Chromium at 1024×600 landscape and 800×1280 portrait;
physical devices have not been tested. Keep tablets powered and configure their
screen timeout for the event. Add a browser shortcut to the home screen.

Internet access is not required during service once the server and tablets are
on the same local network. Tablets do require a connection to this box: the app
does not silently queue offline orders. Reserve 192.168.8.163 for this box in
your router so bookmarks continue working. Use an event Wi-Fi network reachable
by both the box and the tablets; guest Wi-Fi client isolation can block it.

This installation is served over local HTTP. Public access and HTTPS require a
domain/network plan and have not been configured.

## Operations and recovery

- Status: `./olgfeast.sh ps`
- Logs: `./olgfeast.sh logs --tail=100 -f`
- Backup now: `./scripts/backup.sh`
- Daily backup timer: `systemctl list-timers olgfeast-backup.timer`
- Backups: `backups/olgfeast-*.dump` (owner-readable only)

Backups run daily at 06:00 in the box's time zone. Keep an additional copy on
another device: the scheduled copies are on the same disk as the database.
Backups contain account and order data. The pre-upgrade backup was restored to
an isolated rehearsal database and migrated before deploying this version.

Restore rehearsal (use a NEW database name; never overwrite the live database):

```sh
./olgfeast.sh exec -T db createdb -U olgfeast restore_check
./olgfeast.sh exec -T db pg_restore -U olgfeast -d restore_check --no-owner --no-privileges < backups/CHOSEN.dump
./olgfeast.sh exec -T db psql -U olgfeast -d restore_check -c 'SELECT count(*) FROM orders;'
```

For an application rollback, the previous images are retained as
`olgfeast-backend:pre-modernization` and `olgfeast-frontend:pre-modernization`.
Stop incoming orders, take a fresh backup, and use an isolated restored database
with those images. Do not run a destructive schema downgrade on new event data.

## Development and verification

Changes live on the local `event-tablets` branch. CI now requires backend,
frontend, and PostgreSQL/browser integration checks before publishing versioned
ARM64/AMD64 images. No changes have been pushed to GitHub automatically.

```sh
cd fastapi_app
../.venv/bin/python -m pytest tests
cd ../frontend
npm ci
npm run lint
npm test
npm run build
```

`compose.ci.yml` creates an isolated integration stack on ports 3002/8002.
`seed_test.py` refuses to run unless `ENVIRONMENT=test`; set
`E2E_ADMIN_PASSWORD` before seeding. Browser tests use
`npx playwright test -c playwright.event.config.ts` with that password.
`scripts/check_concurrency.py` additionally verifies simultaneous checkout
retries against PostgreSQL, with `E2E_ALLOW_TEST_WRITES=1` set for that test stack.
Never run these write-producing checks against the production database.
